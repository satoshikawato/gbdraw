## Implementation and equivalence argument

The growing scan count predates S06: the S01 and post-S06 merge functions and their executable dependencies are identical. It describes scaling as input anchors increase, not a regression caused by S06. S06 removed normal path enumeration; S07 addresses this separate old merge cost.

The measured chain case justifies a private optimization: the frozen 1200-anchor
merge visits 478,800 candidates and repeatedly materializes growing paths with
160,398 input anchor references. Actual Gallery settings have no conflict calls;
they provide a small-overhead check, not evidence of quadratic real-data merging.

The owner and canonical path remain `analysis/collinearity.py`:
`cluster_lossless_collinearity_anchors` → initial clusters → merge → existing
filter/final sort/renumber. No extra analysis class, persistent index, cache,
public API or compatibility path is introduced. Ordinary non-increasing
architecture evidence applies; no S07 exception trigger. Roll back the S07
production diff together; inputs, saved formats and S06 representation need no
conversion.

- One query-sorted anchor list per pair with at least two clusters supplies
  `bisect_right(query_min)` / `bisect_left(query_max)`, retaining strict bounds
  and duplicate row multiplicity. Subject comparison remains strict. A local
  membership set is built only when a candidate reaches the interior subject
  interval; membership exclusion uses the same anchor value semantics.
- The private count helper takes path-sorted sequences and query-sorted
  candidates. With no `max_conflicts` it returns the exact count. Its sole
  production consumer needs a boolean and stops at `max_conflicts + 1`.
  No approximate value escapes as an exact count or into metadata.
- Initial cluster construction already path-sorts every block. The compatibility
  predicate requires `right.query_order - left.query_order - 1 >= 0`, so an
  accepted concatenation strictly increases query order. This preserves the
  whole path order even with tied or duplicated orders inside input clusters.
  First/last anchors can therefore be read directly, with no endpoint sort.
- The current path borrows the first immutable anchor tuple until the first
  successful merge, then creates one private list and extends it. It creates
  the resulting block once when the run closes. Unmerged blocks retain their
  original object/attributes. Final block construction still uses the original
  sort and score sum, so floating-point summation order is unchanged.
- Initial clustering, candidate order, preserved singleton blocks, min_anchors,
  final sort, renumbering, block IDs and all anchor attributes are unchanged.
  Frozen original scan/sort/copy logic exists only in
  `tests/prototypes/cluster_merge.py`; production never imports it.

Residual complexity: sorting the query index is O(N log N), and each conflict
interval lookup is O(log N + k) for k visited query candidates, with boolean
short-circuiting. When an interior subject candidate exists, constructing the
cluster-exclusion set still costs O(|left| + |right|). Repeated dense conflict
gaps can therefore retain quadratic work. This describes the remaining implementation,
not a mathematical lower bound; further indexing or exclusion-work reduction
would require representative evidence of benefit. Final sorting, cluster ordering,
initial clustering and public result materialization remain; the whole algorithm
is not claimed to be linear. Python list growth has its usual allocation and
reference-moving costs; the counters describe explicit source-level work, not
CPython allocator internals.
