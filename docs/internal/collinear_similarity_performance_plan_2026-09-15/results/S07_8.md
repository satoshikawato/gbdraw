## Pre-implementation decisions

Preflight: **IMPLEMENT_EXISTING_AUTHORITY**. Latest architecture/Product ratchets,
OIPC revision 6 (PD-OI-004/005/006/007/018/021/023), comparison semantics and Session
compatibility preserve the complete supported outcome. No new outcome or ambiguity,
so EVIDENCE_REQUIRED / PRODUCT_DECISION_REQUIRED / NOT_ALLOWED do not apply.
Same two owners, callers, public signatures, validation, cache and persisted formats.
No added owner/path/compatibility path; ordinary non-increasing evidence applies.
S07 approval, S06 future merge Review and S05 rejection remain unchanged.

A: pandas namedtuple `_asdict()` already creates a new ordered dict. Aggregation
copies it again solely before `update`. Remove the outer dict allocation; the
consumer still receives all representative columns in the same order. One full
row dict per accepted pair disappears; no added retention. Keep scalar conversions:
private object-dtype callers can supply stateful `__float__`, so repeated reads
cannot universally be replaced by rank components. Keep coordinate parsing:
`sys.maxsize` is both a valid coordinate and the rank sentinel for invalid input.

B: representative selection reads the same immutable four-field member rank four
times. Fetch it once in a local key function; same key and min traversal, no cache.
Every component member is an anchor-edge endpoint, and the first rank is always
accepted when absent, so all lookups exist. Remove four eagerly constructed
default rank tuples and infinity conversions per member too.
At return, anchor member lists are retained for all groups in an intermediate dict
only to be consumed once by the RBH mapping. Build each final tuple immediately;
retain one temporary list at a time, instead of all anchor lists and the extra dict.
Direction order, all support calculations and fixed/expanded snapshots stay intact.
Do not replace candidate full sort: nonfinite private support keys do not define
a total order. With supports `[1, 1, NaN, 2]`, diagnostic scores all zero and IDs
`0,1,2,3`, full sort selects IDs `0,1`; `heapq.nsmallest(2)` selects `3,0`.
All candidate evaluation/exception order remains unchanged.

C: `_unit_sort_key` materializes four lists, then reads each only for its independent
minimum. Use four generators in the same attribute order; no fusion that would
change conversion errors. Four O(m) lists become one live generator (O(1)). Alias
construction tests membership by scanning a list on every append. Use one ordered
dict as the sole alias collection; string conversion and first occurrence order
remain identical and tuple(keys) is the same output. Its O(a) hash table may have
higher bytes than the old list, but lives only within one unit's alias construction.
Do not combine group minima with first-member or lexicographic tuple selection.

A/B/C will be applied and checked sequentially; disjoint production hunks permit
individual rollback. No S08, new cache, runtime, scheduling or authority changes.

hash-table cost, limited to one `_unit_aliases` call. No persistent cache or new
index survives a call. End-to-end allocation effects are reported separately.

## Reassessment of the dominant work

These figures come from the existing **S07.7 instrumented profiles**, not a new
run, current-source timing, or an estimate of removable seconds. Parent and child
times overlap. The review ledger extracts the exact rows and source report hashes.

| Case / operation | Calls | Profile seconds | Fraction of profiled post-search |
| --- | ---: | ---: | ---: |
| Vibrio ON / HSP aggregation | 31; 80,888 HSP rows | 2.212038 | 31.32% |
| Vibrio ON / covered length, including interval merge | 155,844 | 0.515917 | 7.30% |
| Vibrio ON / anchor-core groups | 1 | 1.754078 | 24.83% |
| Vibrio OFF / numeric coercion and validation | 40 | 0.281213 | 23.92% |
| Vibrio OFF / Python finite-check generator (inside previous row) | 685,860 | 0.132791 | 11.29% |
| Vibrio OFF / unit aliases | 24,027 | 0.144001 | 12.25% |
| Vibrio OFF / unit sort key | 24,027 | 0.027968 | 2.38% |

The stronger HSP candidate is the coverage reduction: the only production
consumer of `_merge_coverage_intervals` is `_covered_length`. It currently creates
a sorted cleaned list, a slice, a merged list and a tuple, then traverses the
merged intervals again to compute a scalar. Eliminating intermediate merged
containers is a concrete hypothesis. However, preserving the private tuple API
with a shared generator adds generator overhead; duplicating the union algorithm
would add another owner. Neither a net time reduction nor an acceptable final
implementation has been demonstrated. The 0.516 seconds cannot be claimed as
savings. Reusing raw rank coordinates also remains blocked by the valid
`sys.maxsize`/missing sentinel collision and stateful private scalar conversions.

A second candidate is the numeric finite check. After `pd.to_numeric`, it still
iterates over every numeric cell in Python and runs `float` plus `math.isfinite`.
A vectorized equivalent could remove Python dispatch while retaining validation.
It needs proof for nullable/object/complex data, conversion failures and warning
behavior; dropping validation or using a validated flag is not an alternative.
This helper is outside the three edited local owners' functions and has wider
callers. It has not been changed or measured in S07.8.

The group profile does not establish that all 24.83% is redundant. Result
construction alone includes 10,385 required member objects (0.254874 seconds)
and annotation-name metadata (0.248183 seconds). The support-candidate count in
Hep Similarity is only 122; top-2 selection also has a concrete NaN ordering
counterexample. Neither the small rank lookup changes nor top-2 is supported as
a major reduction by these observations.

For unit construction, the alias path is larger than the sort key, but replacing
list membership by a dict has already failed to establish a practical improvement
in this candidate. The real Vibrio profile has 24,027 proteins and 24,027 units;
the 100-CDS synthetic alias example is not evidence of representative speedup.
The four-generator sort-key change targets only a 0.028-second profiled region.

**Still unresolved:** useful end-to-end post-search savings, code-versus-host
attribution of the observed regressions, and adoption based on performance.
This reassessment does not start another timing campaign, bypass the three-sample
limit, or present a new untested idea as an implementation result.
