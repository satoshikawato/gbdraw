### 12.6 threaded LOSATP の停止の原因と修正（2026-09-30）

- 原因は 2 段ある。
  - 引き金（browser engine）: Chromium 149 では、別の thread が shared memory を grow した直後に `memory.copy` と `memory.fill` が `memory access out of bounds` で trap する。通常の load・store は影響を受けない。LOSAT なしの engine 単体試験で、両命令とも 5 回中 5 回再現した。LOSAT の allocator（wasi-libc の dlmalloc）は並列段階で memory を grow するため、trap は job 単位で 0.5〜9%（負荷に依存）起きる。
  - 停止（gbdraw の不具合）: trap した WASI thread は job worker にだけ報告していた。job worker は `wasi.start()` の中で block しているため、報告を読めない。他の thread は trap した thread の仕事を待ち続け、job は完了せず、Generate は Processing のまま止まった。
- 以前の 80 s の `UNKNOWN` 失敗も同じ原因で、trap が job の main thread で起きた場合である。
- 修正 1（184d06a1、PR #647）: trap した thread は job ごとの `BroadcastChannel` で page に報告し、page はその job を既存の `fail` 経路で終える。同じ負荷（200 job、8 × 16）で、修正前は 3 回中 2 回が停止し、修正後は 3 回とも速やかな error で、停止は 0 回だった。
- 修正 2（23ddd757）: Owner-delegated の判断。LOSAT の job は決定的なので、main thread または WASI thread が `WebAssembly.RuntimeError` で終わった job を、同じ実行方式のまま最大 2 回やり直す。Auto は、それでも失敗した場合に既存の serial fallback へ移る。trap でない失敗は、やり直さずに直ちに終える。
  - 採らなかった案: explicit Threaded の暗黙の serial 化（利用者の選択を変えるため）、LOSAT の Wasm を大きな初期 memory で作り直すこと（別 project の build で、競合を減らすだけで無くさない）、V8 への報告（外部への行為のため Owner に残す）。
- 検証: LOSAT の unit test は 54 passed（新規 5 件は、やり直しの成功、上限後の失敗、trap でない失敗、Auto の fallback、thread worker の報告）。Playwright の fault spec と実 threaded LOSATP test は 2 passed。H-GUI-08（25 job、Threaded 32、4 runs × 8 threads）は 2 回とも 140 s で完了し、`--check` は一致した（e4e84141 で画像を再生成、「Current:」なし）。
- 残り: trap の件数は UI に表示されず、console の warning だけに出る。error の要約は上限を超えた場合も汎用の `UNKNOWN` である。Chromium の不具合そのものは残る。
