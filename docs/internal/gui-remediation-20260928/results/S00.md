## 4. 計測定義（候補測定前に固定）

S00 で固定し、S03 以降の候補も同じ定義・runner・入力で比較する。候補を通すための入力縮小、後付け除外、閾値緩和はしない。

- **Runner**: 第 2.4 節の機械と browser。CI の `playwright-performance` job（ubuntu-latest、dev push のみ、15 分上限）は別 runner であり、この予算の判定には使わない。runner を変える場合はその runner で baseline を取り直す。
- **開始点**: 操作前に arm した後の最初の trusted `pointerdown` または `keydown` の `event.timeStamp`。Playwright の actionability 待ちは含まない。
- **可視反映**: DOM 述語が真になった最初の animation frame の rAF から MessageChannel で post した task の実行時刻。述語は比較切替＝対象ボタンの `border-blue-500`、LOSAT 切替＝対象ボタンの `aria-pressed="true"`、通常入力＝`#output-prefix` の value、blur＝focus 移動、Generate 受付＝Generate ボタンの `disabled`。handler 時間や spinner 表示だけでは判定しない。
- **Settlement**: `processing`、`labelReflowProcessing`、`sessionImportPending`、History の `capturing`/`restoring` がすべて偽、diagram Worker の helper/run 要求がすべて応答済み、可視反映が観測済みで、かつその後を含む 750 ms の間 DOM mutation、long animation frame、longtask、History revision 変化がない。終点は最後の活動時刻と可視反映時刻の遅い方。60 s 以内に成立しない sample は失敗とし、除外しない。Generate はさらに、開始後に `processing` が真になり、その後偽になった周期を必須とする（120 s 以内に真にならなければ未受付の失敗）。
- **状態変化の assert**: 各 sample の前後で `linearComparisonGlobalAction`、`losatProgram`、入力値、Result 数・error を比べ、対象の選択が実際に変わったことを assert する。History undo 数も記録する。
- **cold/warm**: page の新旧では決めない。app-lifecycle の Worker tracking で、その Generate 中に diagram Worker の construction/initialization が 1 増えたら cold、増えず run が 1 増えたら warm。
- **除外**: 事前宣言した warm-up（各 page・state・操作・方向の最初の 2 回）だけ。GC、外れ値、遅い page は除外しない。
- **標本数**: warm 操作は 3 fresh page × 7 回 = 21 回以上。cold Generate は 1 page 1 回で 3 回（記述統計のみ。20 回規則の対象外）。
- **提案予算（S03 で判定）**: 可視反映 p95 ≤ 100 ms かつ max ≤ 250 ms。比較切替の settlement p95 ≤ 200 ms。操作窓内に ≥ 100 ms の long animation frame がないこと。比較・LOSAT 切替・通常入力の窓で diagram Worker の helper/run と LOSAT Worker の生成・送信が 0。
- **Generate 完了時間の許容差**: 同じ runner・入力・harness で、候補の warm Generate 完了時間（押下→processing 解除）の中央値 ≤ dev baseline 中央値 12,176 ms × 1.05、p95 ≤ dev baseline p95 12,911 ms × 1.10（各 21 回以上）。cold Generate（n=3）は記述統計とし、中央値が baseline の 1.10 倍を超えたら原因を調べる。main（中央値 5,848 ms）は参照値であり合否基準ではない。

呼出回数は V8 precise coverage（`Profiler.startPreciseCoverage({callCount: true, detailed: false})`）で main thread の関数ごとに取る。操作直前の `takePreciseCoverage` で counter を reset し、settlement 後に再取得する。時間計測とは別 pass。Worker isolate は対象外で、Worker 側は postMessage 数で見る。
